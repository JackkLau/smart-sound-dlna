# 本地电影磁力库 · 产品与实施计划

规划基线为 tv-dlna 桌面版 0.10.1（`607cf16`），日期为 2026-11-27。首版覆盖电影和独立短片，沿用 Windows x64、Apple Silicon 和 Intel Mac。剧集分季分集编目留到第二阶段。

## 首版收录规则与实现（0.11.0）

影片以豆瓣条目编号区分。首映年份从 1990 年到本机当前年份（两端均含），豆瓣评分以整数十分位存储，最低 80。影视剧集、无评分及低于门槛的电影不进入可见片库。较新的评分可撤下或恢复影片，人工关联与排除决定保留。评分采集日期、条目是否找到磁力、节点能否下载分别记录或展示。

首批数据来自公开榜单和逐条核对的片单。应用能读取豆瓣公开榜单并续更；完整商业元数据接口的访问资格仍待确认。资源匹配首版采取人工确认策略，已有可核查发布依据的开放电影版本随应用初始化。数据库使用操作系统的 SQLite（macOS 的 sqlite3、Windows 10 及以上的 winsqlite3）。下文保留设计目标与后续扩展项；实际使用入口和片单格式见项目 README。

## 用户能完成什么

用户在「影视 → 资源库」输入中文片名，先看到本地已收录结果。点击「联网找资源」，选定含原名、导演和年份的影片后，应用到已启用的来源搜索，列出版本、来源和匹配理由。高可信结果自动归档，模糊结果由用户确认。下次离线也能查到已归档条目。点击某个版本的「下载」才会选目录、启动现有影视下载器，完成后可载入影片并投屏。

| 优先级 | 功能 | 首版交付标准 |
| --- | --- | --- |
| P0 | 影片建档 | 按片名搜索或按已知豆瓣条目 ID 定位。展示中文名、原名、别名、上映年份、导演；评分带来源和更新时间，海报与简介按来源允许的范围显示。可手工建档或从资源来源补齐字段。 |
| P0 | 网上找版本 | 可查单片，也可导入含片名、年份或豆瓣 ID 的片单，点击「建立资源库」后逐片检索。以原名、中文名、别名分别检索，年份用来消歧。采集直接发布的磁力链接，或从真实的 v1 种子生成磁力链接，记录原始发布页。 |
| P0 | 匹配与确认 | 展示版本名、片名匹配依据及已知的分辨率、语言、体积；未知留空。可确认、改挂、拒绝。重抓时保留人工决定。预告、花絮和合集单独处理。 |
| P0 | 本地检索与维护 | 能按中外文名、年份和有无资源筛选；每部电影展示多个版本，重复来源折叠。可刷新单片、重试失败来源、从剪贴板补录或移除关联。断网仍可浏览。 |
| P0 | 下载与投屏 | 复用现有影视下载器，选择目录、查看进度、完成后载入一个文件。下载器已忙时保留当前选择；取消选目录后仍停在详情页。 |
| P1 | 扩展 | 关注片单定期增量刷新、增加第二个来源、按季／集／合集编目。优先看首个来源的有效覆盖率与人工纠错量。 |

## 数据来源与采集方法

**豆瓣提供影片身份。** 优先用项目获准使用的搜索和详情接口，用条目 ID 更新同一电影。第一步核对可用凭据、可取字段、限流、缓存期限、展示署名和密钥能否分发。本次查到豆瓣的官方合作入口与版权说明，尚未确认本项目持有接口权限。接口未接通时，可以用用户填写的中外文片名、年份或资源来源的元数据跑通流程；界面标明字段的实际来源。若接口要求服务端保管应用密钥，单独评估代理部署与费用。首版可在本地独立运行。[豆瓣合作入口](https://www.douban.com/about/contactus) · [豆瓣版权声明](https://www.douban.com/about/copyright)

**首个下载来源选 Internet Archive。** 通过高级搜索按电影类别和标题取得候选条目，再按条目标识读取文件清单、发布者和许可记录。按清单里的实际名称读取种子，不猜测下载地址。优先选择权利方发布、公共领域或许可明确的条目，并把依据链接留在资源详情中。中文名未命中时用原名重试；片名搜索也应允许返回零个版本。第二个适配器可接发行方网站或检索 API，按来源限制域名、读取实际发布页，抓取页面公开的 magnet 或种子入口。网页摘要只用于发现候选。[高级搜索](https://archive.org/advancedsearch.php) · [条目元数据 API](https://archive.org/developers/md-read.html)

**用《Big Buck Bunny》做第一个样本。** Blender 标明作品采用 CC BY 3.0；归档条目 `BigBuckBunny_328` 列出了 Torrent 入口。验收时从片名开始，记录找到的条目、许可、真实种子和计算出的 BTIH，再确认种子内有现有影视引擎支持的文件。归档页的上传日期不能充当首映年份。公开条目能检索到和当时有节点可下载，分别验证。[发布方许可](https://peach.blender.org/about/) · [归档条目与下载选项](https://archive.org/details/BigBuckBunny_328)

## 实现方案

**项目接入点。** 前端在 `frontend/src/video/` 增加资源库列表和影片详情，从 `VideoPanel.tsx` 进入。Rust 端增加库查询、采集和持久化模块。通过 Tauri 命令查询本地影片、发起资源搜索、确认候选及按资源 ID 下载。Rust 读取已保存的链接，复用 `video_magnet_start` 背后的选目录和启动逻辑；完成后仍走 `video_magnet_open`。当前影视引擎同时处理一项任务，筛选 MP4、MKV、M2TS。资源库无需安装通用队列使用的 aria2c。剪贴板入口复用现有多链接提取能力，补录结果绑定到当前选中的影片。

**采集与匹配。** 元数据适配器提供“搜索影片、读取条目”，资源适配器提供“搜索候选、解析发布页或文件清单”。后台流程按下列顺序执行：

1. 保存选中的影片身份和别名。标题做 Unicode、大小写、空白和标点归一化，保留续集编号、季集号及原文。既有豆瓣 ID 命中时更新同一记录；片名相同的不同作品可共存。
2. 片单建库时先逐行解析片名、年份或外部 ID。可唯一确定的影片进入采集任务，歧义行单独列出；任务页展示已处理影片、新收录版本、待确认、无结果和失败项，并可取消后续任务。对启用的来源按片名变体查询，限制每源页数、请求并发与超时。持久化每个“影片 × 来源”的任务、分页进度和上次成功时间；遇到 429 按 Retry-After 延迟，断网或退出后可重试。成功写入一页后再推进游标。限流、无结果、部分来源失败分别反馈。
3. 对每条候选保留片名、发布页、发布者、许可依据及可验证的版本信息。直接 magnet 复用 BTIH 解析；对 v1 种子取原始 bencode 中 `info` 字典的编码字节计算 SHA-1，保留引擎支持的公开 Tracker。20 字节 BTIH 统一存储，十六进制和 Base32 写法归一。只有 HTTP 视频链接的条目可保留来源页；纯 v2 种子标记暂不兼容。采集阶段只取页面、元数据与种子文件。[BitTorrent v1 规范](https://www.bittorrent.org/beps/bep_0003.html)
4. 一致的作品外部 ID 可作为强依据；缺少共同 ID 时，要求片名或核实过的别名吻合，结合可比的上映年份及其他区分信息。已知年份冲突、同名多部、合集范围不明或只有模糊片名时送人工确认。来源上传年、修复版发行年与首映年各自保留语义。自动策略上线前先用标注集校验，冲突优先级高于匹配分。
5. 同一 BTIH 的多条发现合并成一个资源，保存多个来源。同一电影的不同 BTIH 分开显示。用户拒绝或改挂后，刷新保留决定。来源页面失效标记到对应来源，只有下载时的引擎反馈才更新下载观测；零节点与链接失效分别显示。

**SQLite 结构。** 建议 Rust 使用 `rusqlite` 的 bundled SQLite，在桌面应用数据目录创建 `movie-library.sqlite3`。启用外键和版本化事务迁移；网络请求放在事务外。首版用规范化标题索引处理精确匹配，短中文片名支持子串查询。达到性能门槛后依据实测采用 FTS5 trigram，并保留一、二字中文查询路径。[SQLite FTS5](https://www.sqlite.org/fts5.html)

| 表 | 存什么 | 关键约束 |
| --- | --- | --- |
| `movies`、`movie_aliases` | 本地主键、展示片名、原名、首映年份、导演、可检索别名 | 片名不作唯一键；同片别名去重。 |
| `movie_external_ids` | 本地电影与外部条目的对应、元数据来源、可缓存字段及更新时间 | `(provider, external_id)` 唯一；可按源刷新、过期或清理。 |
| `resources` | 标准化 BTIH、版本名、已知大小和格式 | `infohash_v1` 唯一；未知大小用 NULL。 |
| `resource_sources` | 资源的来源条目、实际链接或种子入口、发布页、许可依据、首次和最后发现时间 | 按资源与来源定位符去重；一个资源可有多条可追溯来源。 |
| `movie_resources` | 电影与资源的对应、匹配依据、待确认／接受／拒绝、人工决定 | `(movie_id, resource_id)` 唯一；允许一个合集对应多部作品，经确认后关联。 |
| `sync_jobs` | 来源、电影、状态、游标、下次重试时间及最近错误 | 同片同源最多一个活动任务；重复请求复用该任务。 |

**界面的三个动作。** “联网找资源”只更新候选；“收录”保存或修正关联；“下载”交给下载器。详情可查看原始发布页和检查时间。分页查询、采集与下载独立，联网失败时仍可打开已有详情。在“无匹配”“来源暂不可用”“找到版本但暂无兼容文件”三种情况下给出不同反馈。

## 实施顺序与验收

估算假设为一名熟悉现有 Rust/React 工程的开发者、首版一个自动资源来源，包含开发与回归；豆瓣合作等待时间另计。

| 阶段 | 预计工作日 | 交付与退出条件 |
| --- | --- | --- |
| 1. 验证数据源 | 1–2 | 核实豆瓣接入路线。用真实公开影片演示“片名 → 来源页 → 种子 → BTIH”，记录可获取字段、许可及是否有兼容视频。保存可重复使用的最小测试样本。 |
| 2. 本地片库 | 2 | 完成 SQLite 迁移、电影与别名录入、列表、详情和本地搜索。重启后数据一致，两个同名重拍版可独立检索，一至二字中文片名有结果。 |
| 3. 自动采集与关联 | 3–4 | 接入第一个资源来源及可用的元数据来源，完成幂等写入、限流重试和人工确认。以 10 部片的导入片单验证批量建库，覆盖同名片、别名、重拍、预告和重复发布；断网重试只处理未完成项。 |
| 4. 下载与回归 | 2–3 | 连接影视下载入口和完成后的载入流程；在可控种源上从资源库启动下载并验证文件，再做一次真实来源冒烟。Windows x64、两种 Mac 均验证数据库打开、中文搜索与下载入口。 |

**首版验收目标（尚待实测）。** 建议准备至少 30 个人工标注的候选，覆盖同名、不同年份、别名、同一 BTIH 多来源以及无资源；同名冲突组自动错挂 0 次，单独报告自动匹配的覆盖率。对同一影片连续刷新三次、再做一次中断恢复，资源数量与来源归属应稳定。以 1 万部电影、5 万条资源为性能样本，在注明配置的参考电脑上，本地常用搜索首屏 P95 目标为 300 毫秒以内。正式开发前先验收阶段 1，再据实际资源覆盖率调整来源优先级。
